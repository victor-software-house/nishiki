L ### What did we do here?
T 24 text.html.markdown
L 
L Although this was a simple test it's been enough to demonstrate a few
T 69 text.html.markdown
L things about how Catch2 is used. Let's take a moment to consider those
T 70 text.html.markdown
L before we move on.
T 18 text.html.markdown
L 
L * We introduce test cases with the `TEST_CASE` macro. This macro takes
T 70 text.html.markdown
L   one or two string arguments - a free form test name and, optionally,
T 70 text.html.markdown
L   one or more tags (for more see [Test cases and Sections](#test-cases-and-sections)).
T 86 text.html.markdown
L * The test automatically self-registers with the test runner, and user
T 70 text.html.markdown
L   does not have do anything more to ensure that it is picked up by the test
T 75 text.html.markdown
L   framework. _Note that you can run specific test, or set of tests,
T 67 text.html.markdown
L   through the [command line](command-line.md#top)._
T 51 text.html.markdown
L * The individual test assertions are written using the `REQUIRE` macro.
T 71 text.html.markdown
L   It accepts a boolean expression, and uses expression templates to
T 67 text.html.markdown
L   internally decompose it, so that it can be individually stringified
T 69 text.html.markdown
L   on test failure.
T 18 text.html.markdown
L 
L On the last point, note that there are more testing macros available,
T 69 text.html.markdown
L because not all useful checks can be expressed as a simple boolean
T 66 text.html.markdown
L expression. As an example, checking that an expression throws an exception
T 74 text.html.markdown
L is done with the `REQUIRE_THROWS` macro. More on that later.
T 60 text.html.markdown
L

L ## Test cases and sections
T 26 text.html.markdown
L 
L Like most test frameworks, Catch2 supports a class-based fixture mechanism,
T 75 text.html.markdown
L where individual tests are methods on class and setup/teardown can be
T 69 text.html.markdown
L done in constructor/destructor of the type.
T 43 text.html.markdown
L 
L However, their use in Catch2 is rare, because idiomatic Catch2 tests
T 68 text.html.markdown
L instead use _sections_ to share setup and teardown code between test code.
T 74 text.html.markdown
L This is best explained through an example ([code](../examples/100-Fix-Section.cpp)):
T 84 text.html.markdown
L 
L ```c++
T 6 text.html.markdown
L TEST_CASE( "vectors can be sized and resized", "[vector]" ) {
T 61 text.html.markdown
L     // This setup will be done 4 times in total, once for each section
T 70 text.html.markdown
L     std::vector<int> v( 5 );
T 15 text.html.markdown
T 16 text.html.markdown meta.tag.other.unrecognized.html.derivative punctuation.definition.tag.begin.html
T 19 text.html.markdown meta.tag.other.unrecognized.html.derivative entity.name.tag.html
T 20 text.html.markdown meta.tag.other.unrecognized.html.derivative punctuation.definition.tag.end.html
T 28 text.html.markdown
L 
L     REQUIRE( v.size() == 5 );
T 29 text.html.markdown
L     REQUIRE( v.capacity() >= 5 );
T 33 text.html.markdown
L 
L     SECTION( "resizing bigger changes size and capacity" ) {
T 60 text.html.markdown
L         v.resize( 10 );
T 23 text.html.markdown
L 
L         REQUIRE( v.size() == 10 );
T 34 text.html.markdown
L         REQUIRE( v.capacity() >= 10 );
T 38 text.html.markdown
L     }
T 5 text.html.markdown
L     SECTION( "resizing smaller changes size but not capacity" ) {
T 65 text.html.markdown
L         v.resize( 0 );
T 22 text.html.markdown
L 
L         REQUIRE( v.size() == 0 );
T 33 text.html.markdown
L         REQUIRE( v.capacity() >= 5 );
T 37 text.html.markdown
L     }
T 5 text.html.markdown
L     SECTION( "reserving bigger changes capacity but not size" ) {
T 65 text.html.markdown
L         v.reserve( 10 );
T 24 text.html.markdown
L 
L         REQUIRE( v.size() == 5 );
T 33 text.html.markdown
L         REQUIRE( v.capacity() >= 10 );
T 38 text.html.markdown
L     }
T 5 text.html.markdown
L     SECTION( "reserving smaller does not change size or capacity" ) {
T 69 text.html.markdown
L         v.reserve( 0 );
T 23 text.html.markdown
L 
L         REQUIRE( v.size() == 5 );
T 33 text.html.markdown
L         REQUIRE( v.capacity() >= 5 );
T 37 text.html.markdown
L     }
T 5 text.html.markdown
L }
T 1 text.html.markdown
L ```
T 3 text.html.markdown
L 
L For each `SECTION` the `TEST_CASE` is **executed from the start**. This means
T 77 text.html.markdown
L that each section is entered with a freshly constructed vector `v`, that
T 72 text.html.markdown
L we know has size 5 and capacity at least 5, because the two assertions
T 70 text.html.markdown
L are also checked before the section is entered. This behaviour may not be
T 73 text.html.markdown
L ideal for tests where setup is expensive. Each run through a test case will
T 75 text.html.markdown
L execute one, and only one, leaf section.
T 40 text.html.markdown
L 
L Section can also be nested, in which case the parent section can be
T 67 text.html.markdown
L entered multiple times, once for each leaf section. Nested sections are
T 71 text.html.markdown
L most useful when you have multiple tests that share part of the set up.
T 71 text.html.markdown
L To continue on the vector example above, you could add a check that
T 67 text.html.markdown
L `std::vector::reserve` does not remove unused excess capacity, like this:
T 73 text.html.markdown
L 
L ```cpp
T 6 text.html.markdown
L     SECTION( "reserving bigger changes capacity but not size" ) {
T 65 text.html.markdown
L         v.reserve( 10 );
T 24 text.html.markdown
L 
L         REQUIRE( v.size() == 5 );
T 33 text.html.markdown
L         REQUIRE( v.capacity() >= 10 );
T 38 text.html.markdown
L         SECTION( "reserving down unused capacity does not change capacity" ) {
T 78 text.html.markdown
L             v.reserve( 7 );
T 27 text.html.markdown
L             REQUIRE( v.size() == 5 );
T 37 text.html.markdown
L             REQUIRE( v.capacity() >= 10 );
T 42 text.html.markdown
L         }
T 9 text.html.markdown
L     }
T 5 text.html.markdown
L ```
T 3 text.html.markdown
L 
L Another way to look at sections is that they are a way to define a tree
T 71 text.html.markdown
L of paths through the test. Each section represents a node, and the final
T 72 text.html.markdown
L tree is walked in depth-first manner, with each path only visiting only
T 71 text.html.markdown
L one leaf node.
T 14 text.html.markdown
L 
L There is no practical limit on nesting sections, as long as your compiler
T 73 text.html.markdown
L can handle them, but keep in mind that overly nested sections can become
T 72 text.html.markdown
L unreadable. From experience, having section nest more than 3 levels is
T 70 text.html.markdown
L usually very hard to follow and not worth the removed duplication.
T 66 text.html.markdown

L ## BDD style testing
T 20 text.html.markdown
L 
L Catch2 also provides some basic support for BDD-style testing. There are
T 72 text.html.markdown
L macro aliases for `TEST_CASE` and `SECTIONS` that you can use so that
T 69 text.html.markdown
L the resulting tests read as BDD spec. `SCENARIO` acts as a `TEST_CASE`
T 70 text.html.markdown
L with "Scenario: " name prefix. Then there are `GIVEN`, `WHEN`, `THEN`
T 69 text.html.markdown
L (and their variants with `AND_` prefix), which act as a `SECTION`,
T 66 text.html.markdown
L similarly prefixed with the macro name.
T 39 text.html.markdown
L 
L For more details on the macros look at the [test cases and
T 58 text.html.markdown
L sections](test-cases-and-sections.md#top) part of the reference docs,
T 69 text.html.markdown
L or at the [vector example done with BDD macros](../examples/120-Bdd-ScenarioGivenWhenThen.cpp).
T 95 text.html.markdown
