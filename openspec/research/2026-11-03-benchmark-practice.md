# How comparable projects benchmark a highlighter

## Question

How do other syntax highlighters, and Rust projects in general, measure speed?
What do they measure, on which inputs, with which statistics, and how do they publish it?
What should nishiki's benchmarks copy, and what should they avoid?

This note informs the `bench-methodology` change.
It does not make its decisions.

## Answer

1. No highlighter gates CI on timing.
   [lumis][lumis-workflow] says so in its workflow: "Timings are not a merge gate".
2. Only two projects publish a full comparative method:
   [lumis][lumis-readme] and [syntax-highlighter-bench][shb-readme].
   Pierre publishes the clearest method for a single library.
3. syntect and giallo run Criterion benches of their own code, with no comparison.
   tree-sitter has a custom bytes-per-millisecond loop over parsing only.
   Shiki has vitest benches that compare its own regex engines.
4. Every published comparison mixes setup and steady state somewhere, or compares different amounts of output, or both.
5. No project measures per-line streaming latency as nishiki needs it.
   Pierre measures chunked streaming; nobody else measures streaming at all.
6. No highlighter uses instruction counts.
   nishiki's callgrind gate is already ahead of the field there.
   rustc-perf uses the same idea for the Rust compiler.

## 1. Highlighters

| Project | Harness | Compared with | Setup kept apart | Published |
|:--|:--|:--|:--|:--|
| syntect | Criterion 0.3 | nothing | yes, in its own bench | hand-written README numbers from 2012 hardware |
| tree-sitter | custom loop | nothing | yes | nothing |
| Shiki | vitest bench | its own engines | yes | nothing |
| Pierre | custom loop in Bun | Shiki, tree-sitter, five JS libraries | yes | README tables from one dated run |
| lumis | Criterion, mitata, Benchee, hyperfine | syntect, Shiki, highlight.js, bat | no, in the Rust rows | README tables, regenerated by a task |
| giallo | Criterion 0.8 | nothing | no: the pattern cache is cleared every iteration | nothing |
| syntax-highlighter-bench | custom TypeScript | Shiki, Prism and others | yes | a website and committed JSON |

arborium, inkjet, syntastica, two-face and synoptic have no benchmarks.

### 1.1 syntect

Read at [`4efbec1`][syntect].

- Four Criterion targets: parsing, highlighting, loading, and load-then-highlight.
- Parsing times `parse_line` per line; highlighting times `highlight_line` per line.
- The corpus is a fixed name-to-path map, so `--baseline` comparisons stay valid across commits:
  jQuery 2.1.4 (247,597 bytes), a Rust file of syntect's own (243,245 bytes), an ERB test file and a few more.
- [`benches/parsing.rs`][syntect-parsing] sets 50 samples and a 30 s warm-up.
  Its comment says it avoids lazy regex compilation, but `load_defaults_nonewlines` loads the embedded dump, and the warm-up absorbs the compilation.
- The README's numbers were measured once, by hand, on a 2012 MacBook Pro.
- No CI step runs the benches.

### 1.2 tree-sitter

Read at [`9632b56`][tree-sitter].

- [`crates/cli/benches/benchmark.rs`][ts-bench] parses each grammar's `examples/` files five times and prints bytes per millisecond.
- It also parses every other language's examples, as a stress test of error recovery.
- It reports the mean of per-file speeds, not total bytes over total time, so a small file weighs as much as a large one.
- There is no warm-up, no spread and no outlier handling.
- Query compilation is timed apart from parsing.
- Highlighting is not benchmarked; `highlight --time` prints one wall-clock figure in whole milliseconds.

### 1.3 Shiki

Read at [`de15fd2`][shiki].

- [`bench/engines/engines.bench.ts`][shiki-engines] compares the JavaScript regex engine, the precompiled grammars, and Oniguruma in WebAssembly.
- It runs on Shiki's own samples, for the first 20 languages whose JavaScript output matches Oniguruma's.
- Every highlighter is built before timing, so only steady state is measured.
  The docs describe startup cost in words only.
- The shikijs organisation has no separate benchmark repository.

### 1.4 Pierre's `@pierre/highlights`

Read at [`75e0080`][pierre], for behaviour only; nishiki copies no code.

- [`benchmark/README.md`][pierre-readme] states the method:
  200 ms warm-up, 1.5 s per case, at least 20 samples, the engine order rotated each round, median and p95 reported.
- It measures HTML throughput, tokens, streaming in chunks of 4,096 UTF-16 units, live edits, and peak RSS over five fresh processes.
- It turns Shiki's line and time limits off.
- It says token boundaries differ between the libraries.
- The fixtures have no stated source or licence.
- The README tables come from one run on an Apple M4 Pro, dated 2026-10-05.

### 1.5 lumis, formerly autumnus

Read at [`fd1e4ab`][lumis].

- One harness per runtime: Criterion, mitata, Benchee and hyperfine.
- It compares lumis with syntect, Shiki, highlight.js and bat.
- Four scenarios: one small Rust file, one generated 5 MiB Rust file, ten small Rust files, ten files in ten languages.
- Every row reports a median.
- It checks each output only loosely: longer than the input, and holding `<pre` and `<span`.
- The README says setup is reported apart, but [`scenarios.rs`][lumis-scenarios] builds the highlighter inside each Criterion iteration for both lumis and syntect.
  syntect's `SyntaxSet` load and its lazy regex compilation are then timed on every iteration, while the JavaScript rows exclude setup.
- The Rust benches build with LTO and one codegen unit, which is not what a user's default release build gets.
- The large input is one block repeated, so it rewards caches more than real code does.

### 1.6 giallo

Read at [`9136c2d`][giallo].

- A TextMate engine in Rust on Shiki's grammars, so its output is the closest to nishiki's.
- [`benches/highlight_benchmark.rs`][giallo-bench] clears the pattern cache at the start of every iteration.
  Each figure is then neither cold nor warm.
- Licensed EUPL-1.2, a copyleft licence ([`Cargo.toml`][giallo-cargo]).

### 1.7 syntax-highlighter-bench

Read at [`dcc0a88`][shb].

The most careful method found, though for JavaScript libraries only, and written by the author of one of them:

- one process per library and input, with the library order rotated;
- calibrated batches, an untimed re-warm, and a garbage collection before each batch;
- noisy cells retried, keeping the attempt with the lowest spread, never the fastest;
- a fixed anchor workload measured before and after each segment, to detect a machine that drifts;
- cold start measured as a fresh process minus a bare runtime baseline;
- every input labelled by origin (neutral files, Shiki's samples, a library's own samples, stress inputs), with repository, commit, path, licence and hash;
- size tiers: under 600 bytes, under 3,200, under 32,000, and above;
- ratios across inputs summarised as geometric means;
- caveats it states itself: Shiki writes inline colours while others write classes, and fewer tokens means less work.

### 1.8 nishiki's own earlier comparison

The engine comparison of 2026-10-22 measured hand-written prototypes against Pierre, syntaxmate, irosashi, syntect and tree-sitter on one instabox box.

- It reported per-line and whole-document throughput, cold start to the first coloured line, and streaming latency (p50, p99, maximum).
- It scored fidelity beside speed, by coarse category against Shiki, because the engines name tokens differently.
- Its harness was not kept in a repository, so it cannot be rerun.

## 2. Harnesses

| Tool | Version | Fits |
|:--|:--|:--|
| [criterion][criterion] | 0.8.2, 2026-02-04 | throughput and micro-benchmarks on a quiet box |
| [divan][divan] | 0.1.21, 2025-04-09 | quick in-process allocation counts |
| [gungraun][gungraun], formerly iai-callgrind | 0.20.0, 2026-09-26 | a deterministic CI gate, and DHAT heap counts |
| [tango-bench][tango] | 0.9.0, 2026-10-16 | paired base-and-head timing, still early |
| [hyperfine][hyperfine] | 2.0.0, 2026-10-07 | whole-process cold start |
| [CodSpeed][codspeed] | 6.0.0, 2026-10-21 | a hosted service; data leaves the repository |
| [Bencher][bencher] | 0.6.16, 2026-10-31 | a history tracker, not a harness |

### 2.1 criterion

- Development moved to the [criterion-rs organisation][criterion-move] in November 2025.
- Defaults: 3 s warm-up, 5 s measurement, 100 samples, 100,000 bootstrap resamples, 0.05 significance, 1% noise threshold ([`src/lib.rs`][criterion-defaults]).
- Time per iteration is a regression slope with a bootstrap confidence interval.
  Outliers are flagged by Tukey fences, not dropped ([analysis][criterion-analysis]).
- `Throughput::Bytes` reports MiB/s; `--save-baseline` and `--baseline` compare two runs.
- Each run writes `estimates.json`, so results are machine-readable.
- It has 15 required direct dependencies; `rayon` and `plotters` are default features that can be turned off.
- Its model is one closure timed over many iterations.
  A distribution over lines, or a fresh process per sample, does not fit it.

### 2.2 divan

- No release since April 2025.
- Its `AllocProfiler` counts allocations and bytes, but says that counting affects timing.
- It writes no machine-readable output ([issue 10][divan-json], open since 2023) and compares no baselines.

### 2.3 gungraun

- Runs a benchmark once under callgrind, cachegrind, DHAT or `perf`, with saved baselines and limits such as `ir=0.5%` ([regressions][gungraun-limits]).
- Reports instructions, cache hits by level and estimated cycles, as JSON.
- Needs a `gungraun-runner` binary at exactly the library's version, and valgrind 3.20 or later.
- Its baseline model compares two runs of one bench binary.
  nishiki's gate builds two trees, each with its own `Cargo.lock`, and counts only the second of two passes.

### 2.4 tango-bench

- Since [v0.8.0][tango-080] it runs base and head as two processes kept in lock-step through shared memory.
- The README calls the project early-stage; the design changed in October 2026.

### 2.5 hyperfine

- 2.0 adds `--metrics` for peak RSS, instructions and cycles, and exports JSON per run ([CHANGELOG][hyperfine-changelog]).
- It times a whole process, so exec and loader time sit inside every figure.

## 3. Noise and instruction counts

- rustc-perf gates on `instructions:u` "because it has the least variation" ([collector README][rustc-perf-readme]).
  Its machines run with SMT, turbo, ASLR and swap off ([deployment][rustc-perf-deploy]).
- The [Rust Performance Book][perf-book] warns that layout alone causes "significant but ephemeral" wall-time changes.
  nishiki saw this on 2026-11-03: an edit that only moved code between codegen units shifted Go's counts by 6% ([bench rule 12][bench-rules]).
- [LLVM's benchmarking tips][llvm-bench] list the controls for wall time: ASLR off, the `performance` governor, turbo off, shielded cores, the SMT sibling offline.
- On cloud VMs, the full PMU is exposed only on sizes that own a socket ([AWS perf runbook][aws-pmu]).
  Smaller sizes get basic counters on newer families and none on older ones.
- nishiki's first recorded run, on a Namespace 4x8 with two threads a core, showed the noise this causes:
  C's slowest fixture ran at 19.5 to 25.5 MiB/s across three runs, shell's at 11.6 to 37.3 ([record][record-574fad99]).

## Not verified

1. Whether Namespace or instabox VMs expose `instructions:u` to `perf`.
   This needs one `perf stat` probe on each.
2. criterion's full transitive dependency count; no cargo ran.
3. tango's claim to detect a 1% change in one second.
4. The tinybench settings behind Shiki's `engines` bench.
5. giallo's CI workflows, and Pierre's fixture sources and licences.
